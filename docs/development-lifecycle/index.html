Chapter 2

Development Lifecycle

This chapter follows FFOnto from the first look at the data to a validated knowledge graph. Each section corresponds to one stage of the lifecycle.

Knowledge Acquisition & Conceptualisation

The starting point was the ForestFire-VQA dataset and the first version of FFOnto. The dataset combines drone images, field audio and fire-weather tables with more than a thousand question–answer pairs written about them. Reading those questions shows what people actually want to know: whether smoke is above a detection threshold, whether firefighters wear the right protective equipment, what the FWI trend is, and which hazards a scene contains.

The first version of the ontology had grown without that focus. It contained duplicated concepts, classes that no question used, and properties that connected unrelated parts of the model. Model outputs were stored as if they were facts about the world, which made it impossible to represent two models disagreeing.

The conceptual model for version 2 separates three layers:

The world layer holds what exists: fire events, sites and the entities seen in a scene. The data layer holds what was captured: image, audio and weather records with their metadata. The claims layer holds what models said about the data. Standard ontologies anchor each layer: SOSA for observations, sensors and features of interest, PROV-O for provenance, SKOS for the vocabulary, and Dublin Core for metadata.

Requirements Definition

Requirements were written as competency questions (CQs). Every question in ForestFire-VQA was mapped to the query pattern that would answer it, and questions that share a pattern were grouped. 1,004 dataset questions reduce to 27 competency questions. 291 of the dataset questions are general knowledge (for example, how to treat smoke inhalation) rather than questions about a specific record, so they are answered from documents rather than the knowledge graph.

Two rules followed from this stage. A term enters the ontology only if a competency question needs it, and every competency question must be answerable by one tested SPARQL query.

Implementation

The ontology is written in Turtle and split into modules, so the schema stays small while the vocabulary grows:

  • Core schema (ffonto-core.ttl): 23 classes, 40 object properties and 57 datatype properties in OWL 2 DL. External terms from SOSA, PROV-O, SKOS and Dublin Core are declared locally, so the ontology loads offline.
  • Vocabulary (ffonto-vocab.ttl): 374 SKOS concepts organised with skos:broader. Concepts carry keywords (skos:hiddenLabel) and background knowledge such as required PPE and the actions that mitigate a hazard.
  • Danger rules (danger-rules.ttl): weather and FWI thresholds stored as data.
  • Derivation rules R00–R08: SPARQL CONSTRUCT queries that derive detections, caption concepts, danger conditions, modality conflicts, hazards and the previous weather record.
  • SHACL shapes for data quality, and a JSON-LD context that lifts the raw JSON and CSV files into RDF.
Turtle
ffonto:ModelObservation a owl:Class ;
    rdfs:subClassOf sosa:Observation ;
    rdfs:label "Model observation"@en ;
    rdfs:comment "A claim made by a model about a data record: either a predicted class
        with a confidence (ffonto:predictedClass) or a categorical value for an observable
        property (sosa:observedProperty + ffonto:hasValueConcept)."@en .

ffontov:Pulaski a skos:Concept ;
    skos:prefLabel "Pulaski"@en ;
    skos:inScheme  ffontov:EntityKindScheme ;
    skos:broader   ffontov:HandTool ;
    skos:hiddenLabel "pulaski"@en .

The question-answering assistant built on the graph is evaluated separately, stage by stage: routing, choice of competency question, query execution, answer quality and faithfulness to the evidence. In preliminary runs on held-out ForestFire-VQA questions, routing between the knowledge graph and general knowledge reached 0.985 accuracy, and choosing the right competency question reached 0.767. The end-to-end evaluation is waiting for scene graphs extracted from all dataset images.

Knowledge Graph Construction

Raw records are lifted into RDF in four steps:

  1. Normalise. A Python lifter reads each image JSON, audio JSON and weather CSV row, fixes missing values and builds stable identifiers, for example one site per weather grid cell.
  2. Map. The JSON-LD context turns each field into an ontology term, so confidence becomes ffonto:confidence and event_id links the record to its ffonto:FireEvent.
  3. Load. The graph is stored in GraphDB in one repository with a named graph per source: ontology, vocabulary, image, audio, weather, scene and inferred. The RDFS-Plus ruleset adds subclass and inverse inferences.
  4. Derive. Rules R00–R08 run as SPARQL updates into the inferred graph, which is rebuilt on every load.

The ontology itself is published as HTML documentation, with Turtle, RDF/XML and JSON-LD downloads, at the ontology documentation site.
